# AI 로또 분석기

동행복권 역대 당첨 데이터를 기반으로 최신 회차, 추천 번호, 자주 나온 번호를 확인하는 서비스입니다.

- `frontend`: React + Vite + TypeScript + Tailwind CSS
- `backend`: Hono + Cloudflare Workers + Cloudflare D1
- 배포 구조: Cloudflare Pages(프론트) + Cloudflare Workers(백엔드)

---

## 현재 화면 구성

메뉴는 2단이다. 상단에서 복권 종류를, 그 아래 탭에서 화면을 고른다.

| 경로 | 탭 | 내용 |
|------|----|------|
| `/lotto/results` | 결과 | 회차 뷰어(좌우 이동) · 회차 목록(검색·클릭 이동) · 번호 색상 안내 |
| `/lotto/picks` | 추천 | 추천 번호 5세트 생성 · 다음 회차로 저장 · 백테스트 고지 패널 |
| `/lotto/mine` | 내 번호 | 저장한 번호와 채점 결과 |
| `/pension/results` | 결과 | 회차 뷰어(좌우 이동) · 회차 목록(검색·클릭 이동) |
| `/pension/picks` | 추천 | 추천번호 세트 생성 · 다음 회차로 저장 · 백테스트 고지 패널 |
| `/pension/mine` | 내 번호 | 저장한 번호와 채점 결과 |

`/`, `/lotto`, `/pension` 처럼 탭이 없는 경로는 `results` 탭으로 열린다. 복권을 전환하면 탭은 결과로 돌아간다.

추천 탭 하단의 **백테스트 고지 패널**은 이 추천이 무엇을 바꾸고 무엇을 못 바꾸는지 보여준다.
번호 커버리지·회차 최고 일치는 실제로 올릴 수 있는 값이라 랜덤 대조군과 도달 가능한 상한을
같이 표시하고, 세트 평균 일치는 어떤 방식으로도 `6×6/45 = 0.8` 을 넘지 못한다는 사실을 함께 적는다.
근거는 [docs/PLAN.md](docs/PLAN.md) Phase 1.5 참조.

## 데이터베이스 초기화

최초 1회:

```bash
cd backend
npm run init-db
```

최신 당첨 데이터 동기화 (관리자 토큰 필요, 아래 [관리자 토큰](#관리자-토큰) 참고):

```bash
# 로컬 (backend/.dev.vars 의 ADMIN_TOKEN)
curl -X POST http://localhost:8787/api/sync -H "Authorization: Bearer $ADMIN_TOKEN"

# 운영
curl -X POST https://lotto-analysis-backend.kbaysin.workers.dev/api/sync -H "Authorization: Bearer $ADMIN_TOKEN"
```

참고:
- 한 번에 최대 10회차씩 저장됩니다.
- 1회부터 최신 회차까지 모두 채우려면 여러 번 호출해야 합니다.
- 평소에는 cron 이 매일 자동으로 동기화하므로 직접 호출할 일은 드뭅니다 ([자동 동기화](#자동-동기화)).

### 관리자 토큰

`POST /api/sync`, `POST /api/pension/sync` 는 `Authorization: Bearer <ADMIN_TOKEN>` 헤더가
있어야 실행됩니다. 없거나 틀리면 `401`, 서버에 `ADMIN_TOKEN` 이 설정되지 않았으면 항상 `401` 입니다.
cron 동기화는 토큰과 무관하게 동작합니다.

```bash
# 운영: Workers 시크릿으로 설정 (값은 프롬프트에 입력)
cd backend
npx wrangler secret put ADMIN_TOKEN

# 로컬: backend/.dev.vars (git 에 올라가지 않음)
echo "ADMIN_TOKEN=local-dev-token" > .dev.vars
```

토큰 값 예시 생성: `openssl rand -hex 32`

## 추천 번호 알고리즘

현재 추천 로직은 백엔드 `backend/src/algorithms/lotto.ts`, `backend/src/algorithms/pension.ts`에서 동작합니다.

백엔드 레이어 구조 설명은 `backend/src/ARCHITECTURE.md`를 참고하세요.

### 적용 알고리즘 요약

- 로또: 베이즈식 번호 가중치, 최근 출현 반영, 콜드/과열 패널티, 규칙 가중치 동적 조정,
  세트 간 번호 분산, 인기 조합 회피, 단계별 폴백
- 연금복권: 6자리 무작위 생성, 합계/홀짝/고유 숫자/연속수/중복 필터, 랜덤 폴백
- 백테스트: 평균 일치 수, 최고 일치 수, 번호 커버리지, 인기 백분위, 폴백 비율, 규칙별 성과 진단

### 로또 (`v3.4`)

#### 기본 흐름
1. 전체 당첨 이력과 최근 당첨 이력을 함께 사용해 번호별 점수를 계산합니다.
2. 전체 빈도에는 균등 prior를 더한 베이즈식 posterior를 만들고, 최근 출현 점수와 `50:50`으로 섞습니다.
3. 최근 `15`회에 한 번도 나오지 않은 번호는 콜드 패널티로 가중치를 `50%` 낮춥니다.
4. 최근 `10`회 안에서 `3회 이상` 나온 과열 번호는 가중치를 `30%` 낮춥니다.
5. 가중치 기반 랜덤 추출로 중복 없는 6개 번호를 생성합니다.
6. 최근 당첨 번호가 어떤 규칙을 더 자주 만족했는지 계산해 세트 규칙 우선순위를 동적으로 조정합니다.
7. 세트를 순차 생성하면서 앞 세트가 쓴 번호의 가중치를 `5%`로 낮춥니다 (세트 간 번호 분산).
8. 규칙을 통과한 후보를 `24`개 모아 그중 **인기 점수가 가장 낮은 조합**을 고릅니다 (아래 참고).
9. 세트 규칙까지 통과하지 못하면 공통 규칙만 만족하는 완화 폴백을 다시 시도하고, 그래도 실패하면 랜덤 폴백 세트를 반환합니다.

#### 사용 구간
- 최근 출현 가중치 계산: 최근 `50`회
- 콜드 판정: 최근 `15`회
- 과열 판정: 최근 `10`회
- 규칙 가중치 분석: 최근 `24`회
- 세트별 최대 시도 횟수: `300`

#### 공통 규칙
- 합계: `110 ~ 170`
- 홀수 개수: `2 ~ 4`
- 최대 연속 길이: `2` 이하 (`3연속 금지`)
- 9단위 구간 개수: `3`개 이상

#### 생성 세트
| 세트 | 조건 |
|------|------|
| 홀짝 균형형 | 공통 필터 + 홀수 정확히 3개 |
| 연속 독립형 | 공통 필터 + 연속번호 0개 |
| 합계 안정형 | 공통 필터 + 합계 110 ~ 155 |
| 구간 분포형 | 10단위 구간 4개 이상 분산 |
| 끝수 균형형 | 공통 필터 + 끝자리 모두 다름 |

#### 규칙 가중치 동적 조정
- 최근 `24`회 당첨 번호가 각 규칙을 얼마나 자주 만족했는지 계산합니다.
- `공통 규칙 + 세트 규칙` 동시 만족 비율과 `세트 규칙` 자체 만족 비율을 합쳐 규칙 점수를 만듭니다.
- 점수가 높은 규칙부터 먼저 세트를 생성합니다.
- 생성 응답과 백테스트 응답에 규칙별 가중치 진단값이 포함됩니다.

#### 인기 조합 회피

당첨 **확률**은 어떤 번호를 골라도 `6×6/45 = 0.8`로 같습니다. 바꿀 수 있는 건 **배당**입니다 —
1·2·3등은 당첨금을 당첨자끼리 나누므로, 남들이 덜 고르는 조합이면 같은 당첨에 더 받습니다
(4·5등은 50,000원·5,000원 고정액이라 인기와 무관합니다).

구현은 `backend/src/algorithms/popularity.ts`. 1,243회차의 등위별 당첨자 수로
특징 11개(`≤31` 개수, `≤12` 개수, 합 편차, 연속쌍, 끝수 중복, 용지 격자 열·행 집중,
`max−min`, 홀수 개수, 5의 배수, 10단위 구간 수)를 최소제곱으로 적합했습니다.

측정값 — 적합 400~1043회차, 보고 1044~1243회차(적합에 쓰지 않은 구간), 표본 외 `r = 0.402`.
점수 최하위 20% 선택 시 1인당 당첨금(부트스트랩 2,000회):

| 등위 | 배수 | z | 판정 |
|------|------|---|------|
| 1등 | 1.033배 | 0.37 | 구분 불가 |
| 2등 | 1.140배 | 4.26 | Bonferroni 임계 2.39 통과 |
| 3등 | 1.077배 | 4.48 | 통과 |

**1게임 기대값 520원 → 529원** (환급률 52.0% → 52.9%). 여전히 사는 쪽이 손해입니다.

1등에서 차이가 안 나오는 건 모델 탓이 아닙니다 — **1등 당첨자 중 번호를 직접 고른 사람(수동)은
30.1%뿐**이고 나머지는 자동 64.6% · 반자동 3.7%입니다(최근 200회차). 자동은 균등 무작위라
인기 편향이 없으므로 신호는 수동 몫 안에서만 움직입니다. 수동 비율은 212회차 이후 29~33%로
안정적입니다.

후보 수 `24`는 240회차 × 24시드로 정했습니다. 인기 백분위 52.2(끔) → 13.0,
세트 간 서로 다른 번호 29.11 → 28.82/30. 평균 일치와 회차 최고 일치는 후보 수와 무관합니다.

#### 폴백 단계
- 1차: 공통 규칙 + 세트 규칙
- 2차: 공통 규칙만 만족하는 완화 폴백
- 3차: 완전 랜덤 폴백 (`fallback-random`)

### 연금복권 (`pension-multi-set-v2.2`)

- 0~9 숫자 6자리를 생성합니다.
- 조건:
  - 합계 `22 ~ 34`
  - 홀수 개수 `2 ~ 4`
  - 고유 숫자 `4개 이상`
  - `3연속` 오름차순/내림차순 금지
  - 동일 숫자 최대 `2개`
- 공통 규칙을 통과한 뒤 아래 성향별 규칙 세트로 나눠 추천합니다.
- 최근 당첨 패턴을 기준으로 어떤 성향 세트가 더 자주 맞는지 계산해 추천 세트 우선순위를 동적으로 조정합니다.
- 성향별 규칙을 못 맞추면 공통 규칙만 맞춘 완화 폴백을 다시 시도합니다.
- 최근 연금복권 당첨번호를 기준으로 자리별 숫자 빈도를 반영한 통계 기반 폴백을 추가로 시도합니다.
- 최대 `300`번 시도 후 실패하면 완전 랜덤 6자리 폴백을 반환합니다.
- 현재 생성 세트:
  - `균형형 추천`: 홀수 3개
  - `홀수 집중형 추천`: 홀수 4개
  - `고유수 확장형 추천`: 고유 숫자 5개 이상
  - `저합계 안정형 추천`: 합계 22~28

- 규칙 가중치 동적 조정:
  - 최근 `24`회 당첨번호를 기준으로 각 세트 규칙의 적합도를 계산합니다.
  - `공통 규칙 + 세트 규칙` 동시 만족 비율과 `세트 규칙` 자체 만족 비율을 합쳐 점수를 만듭니다.
  - 점수가 높은 추천 성향부터 먼저 생성합니다.

### 적용하지 않기로 한 것

Phase 0 측정으로 **어떤 선택 규칙을 써도 세트당 기대 일치 수는 `0.8`에서 움직이지 않는다**는 것을
확인했습니다 (100만 회 시뮬레이션: 고정 1-6 `0.7995`, 연속수 `0.7981`, 홀수만 `0.8002`,
무작위 `0.8001`). 추첨이 균등하므로 구조적으로 그렇습니다.

따라서 아래 기법들은 **당첨 확률을 올릴 수 없습니다**. 번호를 고르는 방식을 바꿀 뿐이고,
바꾼 결과는 전부 같은 `0.8`로 수렴합니다.

| 기법 | 판단 |
|------|------|
| 마르코프 체인 | 추첨은 독립이라 상태 전이가 없습니다 |
| 몬테카를로 / Kelly | 기대값이 항상 음수(환급률 52.9%)라 최적 베팅 크기는 0입니다 |
| LSTM / GRU | 학습할 시계열 신호가 없습니다 |
| 유전 알고리즘 | 최적화할 목적함수가 상수(0.8)입니다 |
| 클러스터링 | 군집을 찾아도 당첨 확률에 반영할 경로가 없습니다 |
| 앙상블 생성 | 전략을 섞어도 기대 일치 수는 0.8입니다 |

움직일 수 있는 지표는 둘뿐이고 둘 다 적용했습니다.

- **세트 간 번호 커버리지** — 5장으로 몇 개 번호를 덮는지. 22.26 → 29.12/30 (`v3.3`)
- **인기 조합 회피** — 당첨 시 나눠 갖는 사람 수. 인기 백분위 52.2 → 13.0,
  기대값 520 → 529원 (`v3.4`). 후보를 걸러내느라 커버리지는 29.12 → 28.82 로 조금 내려갑니다

남은 여지는 작습니다. 커버리지 상한은 30이고 거기까지 밀어도 회차 최고 일치는
측정 오차 안에서 움직입니다. 인기 회피는 1등이 예측 불가라 위 수치가 사실상 상한입니다.

분석 기록은 [docs/PLAN.md](docs/PLAN.md)에 있습니다.

| `GET` | `/api/picks` | 저장한 번호 조회 (`?lottery=`, `X-Client-Id` 헤더) |
| `GET` | `/api/picks/next-draw` | 저장 대상 회차 조회 (`?lottery=`) |
| `POST` | `/api/picks` | 추천 번호 한 세트를 다음 회차로 저장 |
| `POST` | `/api/picks/bulk` | 생성된 세트를 한 번에 저장 (최대 10세트, 한도 검사 1회) |
| `DELETE` | `/api/picks/:id` | 저장한 번호 삭제 |
| `POST` | `/api/picks/transfer-code` | 기기 연동용 일회용 코드 발급 (10분, 1회용) |
| `POST` | `/api/picks/claim` | 다른 기기의 코드로 보관함 이어받기 |

`/api/generate/backtest` 응답에는 아래 지표가 포함됩니다.

- `generationQuality.commonRulePassRate` / `relaxedFallbackRate` / `randomFallbackRate`
  — 공통 필터 통과율, 세트 조건 완화·랜덤 fallback 발생 비율
- `baseline.theoretical` — 6/45 초기하분포 이론값. 세트당 기대 일치 수 `0.8`, 표준편차 `0.784`,
  일치 수별 확률과 기대 분포
- `baseline.randomControl` — 같은 회차에 순수 랜덤 세트를 같은 수만큼 채점한 대조군
- `coverage` — 5세트가 덮는 서로 다른 번호 수와 그 상한(`30`)
- `popularity.averagePercentile` / `randomPercentile` — 추천이 달성한 인기 백분위.
  무작위로 고르면 정의상 `50` 이다. 당첨 확률이 아니라 당첨 시 나눠 갖는 사람 수와 관련 있다.
- `baseline.overall` — 추천 알고리즘 전체의 `zScore`, `ci95`, `significant`
  (`|z| ≥ 1.96` 이면 5% 유의수준에서 랜덤과 다름). 같은 회차의 세트 5개는 같은 가중치를
  공유해 상관되므로, 회차별 합계(n = 평가 회차)의 경험 분산으로 표준오차를 계산한다.
  대조군도 같은 방식으로 계산해 두 z를 같은 기준에 둔다.
- `ruleDiagnostics.performance[].zScore` / `ci95` — 세트 규칙별 지표. 규칙당 회차마다 1세트라
  `z = (평균 − 0.8) / (0.784/√n)` 을 그대로 쓴다.

어떤 전략이든 `|z| < 1.96` 이면 랜덤과 구분되지 않는 것으로 본다. 백테스트는 고정 시드로 세트를
생성하므로 같은 데이터면 같은 결과가 나온다. 결과는 최신 회차가 바뀔 때까지 D1 에 캐시된다.
시드 하나의 결과이므로, 유의한 결과가 나오면 다른 시드로도 재현되는지 확인해야 한다.

`/api/pension/generate/backtest` 는 같은 형식(`baseline.theoretical` / `randomControl` / `overall`)을 쓰되,
점수가 **1등 번호와 끝자리부터 연속으로 일치한 자리 수(0~6)** 다. 연금복권720+ 등위가 이 기준이다
(동행복권 [연금복권720+ 소개](https://www.dhlottery.co.kr/pt720/intro) 당첨구조: 2~7등 = 끝 6~1자리, 1등 = 조까지 일치).

- 무작위 기준선: `P(정확히 끝 k자리) = 0.9·0.1^k (k<6)`, `P(6) = 10⁻⁶` → 기대값 `0.1111`, 표준편차 `0.3514`
- `rankHits` — 등위 환산. 추천 번호는 조를 고르지 않으므로 6자리 일치는 `rank2` 로 센다. `bonus` 는 보너스 번호 6자리 일치

연금복권 동기화 예시:

```bash
# 누락 회차 전체 저장
curl -X POST "http://localhost:8787/api/pension/sync" -H "Authorization: Bearer $ADMIN_TOKEN"

# 누락 회차 중 10개만 저장
curl -X POST "http://localhost:8787/api/pension/sync?limit=10" -H "Authorization: Bearer $ADMIN_TOKEN"

# 최신 연금복권 1건 조회
curl "http://localhost:8787/api/pension/results?limit=1"

# 특정 회차 상세 조회
curl "http://localhost:8787/api/pension/results?drawNo=306"
```

### 저장한 번호 채점

추천 탭에서 번호를 저장하면 **서버가 정한 다음 회차**(최신 결과 + 1)로 `saved_picks` 에 들어간다.
동기화(cron·수동) 직후 결과가 나온 회차의 미채점 저장분을 서버가 채점한다 — 로또는 일치
개수와 보너스로, 연금은 끝자리 연속 일치 수로 등위를 매긴다.

로그인이 없어 브라우저가 만든 UUID(`X-Client-Id` 헤더)로 묶는다. 이 값을 아는 사람은 그
저장분을 읽고 지울 수 있으므로 URL 에 넣지 않고 헤더로만 보낸다.

### 기기 연동

다른 기기에서 같은 보관함을 보려면 "내 번호" 탭에서 일회용 코드를 만들어 그 기기에 입력한다.
코드를 쓴 기기가 원래 기기의 식별자를 이어받고, 쓴 기기에 있던 저장분은 함께 합쳐진다.

코드가 곧 그 보관함의 열쇠라 이렇게 제한한다.
- 10자리(`XXXXX-XXXXX`, 0·1·I·O 제외 32자 알파벳). 32¹⁰ ≈ 1.1e15 — 활성 코드 1000개에
  100만 번 추측해도 적중 확률 ~9e-7. 8자리는 같은 가정에서 ~9e-4 라 부족하다
- 수명 10분, 한 번 쓰면 삭제. 새로 만들면 이전 코드는 무효
- 원문을 저장하지 않고 SHA-256 해시만 둔다

## 자동 동기화

Workers cron 으로 자동 동기화합니다 (Cloudflare cron 은 UTC 기준).

| 대상 | cron (UTC) | KST |
|------|-----------|-----|
| 로또 (추첨 직후) | `10 12,13 * * 6` | 토 21:10, 22:10 |
| 연금복권 (추첨 직후) | `40 10,11 * * 4` | 목 19:40, 20:40 |
| 로또 + 연금복권 (그물망) | `30 21 * * *` | 매일 06:30 |

추첨 시각은 로또 토 20:35, 연금복권 목 19:05 입니다. 추첨 직후 cron 을 두 번 거는 건
동행복권 쪽 집계가 늦을 때를 대비한 것이고, 매일 돌리는 건 둘 다 놓쳤을 때의 그물망입니다.
무료 플랜은 계정당 트리거 5개까지라 현재 3개를 씁니다.

- 동기화 직후 저장된 번호를 채점하고, 등위별 당첨자 수를 200회차씩 백필합니다.
  둘 다 할 일이 없으면 그냥 지나갑니다.
- 동기화는 멱등이라 새 회차가 없으면 최신 회차 확인 요청만 나갑니다. 추첨 다음 날 동행복권 쪽 사정으로
  못 받아도 이튿날 다시 받습니다. 발표된 회차를 받지 못하면 Workers 로그에 error 로 남습니다.
- 설정 파일: `backend/wrangler.toml`
